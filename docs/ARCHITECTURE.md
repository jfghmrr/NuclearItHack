# Архитектура решения

## Контекст

Приложение работает на одном устройстве Android без сети. Вход - аудиофайл. Выход - контрактный JSON, служебные данные и экран результата.

По условию задачи проверка идёт автоматически на стандартном эмуляторе ARM с 4 ГБ RAM. Образ, число vCPU и хост стенда неизвестны. Отсюда три главных решения: стадии выполняются строго по очереди, JSON появляется раньше языковой модели, на пути автоматики нет диалогов.

## Компоненты

| Модуль | Назначение |
|---|---|
| `:core` | Чистый Kotlin: контракт и валидатор, слияние, ресемплер, нарезка на срезы, книга говорящих, определение языка, окна, бюджет и сборка протокола, состояния и ошибки, формулы скорости. Тесты идут на JVM |
| `:app` | Интерфейс Compose, очередь и стадии конвейера, служба обработки, хранилище задач, декодер, обёртки sherpa-onnx, служба языковой модели |
| `:engine-llm` | Сборка llama.cpp, мост JNI, генерация с грамматикой GBNF, отмена |

| Процесс | Что в нём работает |
|---|---|
| Основной | Интерфейс и все стадии до записи JSON. Служба переднего плана типа `dataSync`, с API 35 `mediaProcessing`, держит работу при выключенном экране |
| `:llm` | Только языковая модель. Обычная связанная служба. Запись файлов атомарна, поэтому процесс можно завершить в любой момент |

```text
Импорт -> Предпроверка -> Декодирование -> VAD -> Язык -> ASR -> Диаризация окнами -> Слияние
       -> Проверка JSON -> Download/Stenokot/<имя>.json -> пауза 3 с -> LLM в процессе :llm -> Протокол
```

Каждая стадия читает вход с диска и пишет выход на диск. Модель стадии закрывается до начала следующей.

```text
filesDir/jobs/<uuid>/
    job.json          состояние задачи, замена атомарная
    source.<ext>      копия импортированного файла
    pcm16k.wav        единая шкала времени
    vad.json          срезы записи
    lang.json         язык файла
    asr.jsonl         журнал распознавания по срезам
    diar.jsonl        журнал окон диаризации
    turns.json        интервалы говорящих после сшивки
    merged.json       реплики, неизменяемая база
    transcript.json   контрактный файл
    llm_windows.jsonl журнал ответов языковой модели
    protocol.json     протокол
    metadata.json     доказательства прогона
    metrics.jsonl     замеры стадий
    llm_stats.json    счётчики языковой модели
filesDir/speed.json         скорость этого устройства для оценки времени
noBackupFilesDir/models/<версия>/    копия файла языковой модели, отметка llm.READY
Download/Stenokot/<имя>.json
Download/Stenokot/meta/<имя>.metadata.json, <имя>.protocol.json
```

## Основные технические решения

| Решение | Причина |
|---|---|
| ASR раньше диаризации | Ошибка диаризации не затрагивает текст, а резка по говорящим портит распознавание |
| Стадии строго последовательны | Совместная загрузка моделей небезопасна на 4 ГБ |
| Одна тяжёлая задача, порядок по поступлению | Две тяжёлые модели не встречаются никогда, порядок предсказуем |
| JSON записывается до LLM | Сбой LLM не теряет результат, скорость основного пути не зависит от LLM |
| Пауза 3 с после JSON | Автоматике нужно время увидеть файл до старта тяжёлой модели |
| LLM в отдельном процессе | Смерть процесса возвращает память и не трогает интерфейс |
| Язык определяется на срезах GigaAM | Нет лишней модели и лишней загрузки в типичном русском случае |
| Диаризация окнами по 5 минут | Нативный метод держит весь сигнал в куче и строит квадратичную матрицу, поэтому часовой файл целиком не подаётся |
| Чекпойнты после каждого среза и окна | Длинная задача переживает завершение процесса |
| Единая шкала `pcm16k.wav` | Распознавание, диаризация и плеер читают один файл, времена совпадают. Громкость приводится к -23 дБFS только при чтении, файл не меняется |
| Модели внутри APK | Условие задачи: основная работа без сети. ONNX читаются из assets, импорт работает сразу после установки |
| Копия языковой модели только в простое | Копия не конкурирует с распознаванием. На время задачи она останавливается, ждёт только стадия LLM. Копия сверяется с SHA-256 из `config/models.lock` и переживает смерть процесса |
| Хранение в файлах | Запросов нет, база данных лишняя |
| Служба переднего плана | Работа при выключенном экране |
| Текст модели никто не правит | Текст должен оставаться дословным. Поэтому коррекции текста языковой моделью нет |
| Готовые веса без дообучения | Нет открытых русских разговоров с проверенным эталоном и ясной лицензией, а коррекция текста противоречит дословности |

Потоки считаются по формуле `max(2, min(4, производительные ядра, ядра - 1))` для распознавания и языковой модели. Диаризация работает на двух потоках.

Перед каждой стадией приложение сверяет свободную память с бюджетом стадии. Ниже бюджета обработка не останавливается, появляется предупреждение `LOW_MEMORY`. Исключение одно: языковая модель не запускается, если свободно меньше 650 МиБ, статус `SKIPPED_LOW_MEMORY`.

| Стадия | Бюджет, МиБ |
|---|---:|
| Декодирование | 170 |
| Поиск речи | 190 |
| Определение языка, распознавание | 850 |
| Диаризация | 450 |
| Слияние | 100 |
| Проверка и запись JSON | 50 |
| Языковая модель | 650 |

Это бюджеты, а не замеры. Замеры памяти - в [TEST_RESULTS.md](TEST_RESULTS.md).

## Состояния задачи

Основной поток: импорт, предпроверка, декодирование, VAD, определение языка, ASR, диаризация, слияние, проверка, запись JSON, пауза 3 с, языковая модель, готово. Стадии идут строго одна за другой. Одновременно выполняется одна тяжёлая задача, порядок по поступлению.

```text
Queued -> Running(IMPORT..VALIDATE) -> TranscriptReady -> [WaitingModel] -> Running(LLM) -> Done
WaitingModel -> Done(DEFERRED)                               новый импорт, пока копируется модель
Running -> Paused -> Running                                 перегрев
Running -> Interrupted -> Running                            продолжение с чекпойнта
Running -> Failed                                            до появления JSON
Running -> Cancelled                                         отмена пользователем
Queued -> Cancelled                                          отмена в очереди
Failed, Cancelled, Interrupted -> Queued                     запуск заново
TranscriptReady, Running(LLM) -> Done(LlmStatus)             никогда не Failed: JSON уже есть
Done(DEFERRED или SKIPPED_BY_BUDGET) -> Running(LLM) -> Done один повтор после 30 с простоя
```

| Состояние задачи | `txt_status` |
|---|---|
| Задачи нет | `IDLE` |
| `Queued`, ожидание другой задачи | `QUEUED` |
| `Running` | `RUNNING:<STAGE>` |
| `Paused`, перегрев | `RUNNING:<STAGE>`: работа продолжится сама, автоматика не должна считать это сбоем |
| JSON сохранён, 3 с до старта LLM | `TRANSCRIPT_READY` |
| `WaitingModel` | `WAITING_MODEL`: JSON готов, копия модели ещё идёт |
| `Done`, кроме сбоя модели | `DONE` |
| `Done(FAILED)` | `DONE_LLM_FAILED` |
| Нет речи | `DONE` с предупреждением `AUDIO_EMPTY` |
| `Failed`, `Interrupted` | `FAILED:<CODE>` |
| `Cancelled` | `CANCELLED` |

Стадии `<STAGE>`: `IMPORT`, `DECODE`, `VAD`, `LANG_ID`, `ASR`, `DIARIZE`, `MERGE`, `VALIDATE`, `LLM`. Прерывание без известной причины показывается как `FAILED:INTERRUPTED`.

Итог языковой модели `LlmStatus`: `APPLIED`, `PARTIAL`, `DEFERRED`, `CANCELLED_BY_NEW_JOB`, `SKIPPED_BY_BUDGET`, `SKIPPED_LOW_MEMORY`, `FAILED`.

После смерти процесса запись задачи сверяется с файлами на диске. Стадия считается пройденной, только если её результат существует вместе с результатами всех стадий до неё. Если JSON записан, задача завершается с протоколом `DEFERRED`. Если нет, она становится прерванной и продолжается с первой незавершённой стадии.

## Правила и инварианты

Общие правила:

- Текст ASR никогда не редактируется после распознавания. Слияние перемещает целые объекты `Word` и не меняет `Word.text`
- Языковая модель называет тему и помечает номера реплик. Текст пункта, говорящего и время копирует код. Грамматика допускает только настоящие номера реплик окна
- Контрактный JSON записывается до старта языковой модели, с ней и без неё он один и тот же по байтам. При провале проверки он не записывается никуда
- Сбой языковой модели заканчивается состоянием `Done(LlmStatus)` и никогда не делает задачу неудачной
- Новый импорт останавливает работающую языковую модель меньше чем за 1 с. Протокол получает `DEFERRED` и один повтор после 30 с простоя
- Прогресс настоящий: нет придуманных процентов и зацикленной анимации, значения обновляются не чаще раза в секунду

Инварианты слияния:

- Слова не теряются и не меняются
- Время: `0 <= start_ms < end_ms <= длительность + 50 мс`
- Реплики отсортированы по `start_ms`
- Каждое слово входит ровно в одну реплику
- Говорящие идут как `speaker_1..speaker_K` без пропусков, номера выдаются по первому появлению
- Результат детерминирован
- Знак препинания не перемещается отдельно от своего слова

Крайние случаи:

- Тишина даёт `{"transcript":[]}` и предупреждение `AUDIO_EMPTY`
- Неподдерживаемый или повреждённый файл отсеивается на предпроверке, до загрузки моделей
- Наложенная речь даёт один поток слов: каждое слово получает одного говорящего, интервалы реплик могут пересекаться
- Срез, на котором распознавание падает дважды, пропускается с отметкой `SKIPPED_SEGMENT:<номер>` в `metadata.json`. Окно диаризации, которое падает дважды, записывается пустым, отметка `SKIPPED_WINDOW:<номер>`. Иначе запись, убивающая процесс, не дала бы закончить файл
- Если интервалов говорящих нет совсем, текст остаётся, а реплики получают одного говорящего

## Бюджет языковой модели

```text
T_llm = max(15 с, min(0.10 T, 90 с, 0.95 T - t_core))
```

`T` - длительность записи, `t_core` - время всех стадий до JSON.

- Первое окно получает попытку всегда, с пределом генерации 45 с. Копия файла модели и её загрузка в этот предел не входят
- Если первое окно не уложилось в предел, статус `SKIPPED_BY_BUDGET`
- Окна идут в таком порядке, что любая начальная часть покрывает запись равномерно: сначала середина, затем середины половин. Бюджет может закончиться на любом окне
- Размер окна 450 токенов, для записей длиннее 15 минут 300 токенов. Соседние окна перекрываются на одну реплику, реплика не делится никогда. Окна с редкой речью, ниже 30 слов в минуту, пропускаются: чаще всего это музыка или шум
- `DEFERRED` и `SKIPPED_BY_BUDGET` получают один повтор при простое от 30 с. Отмена новым импортом повтор не расходует
- Если окна обработаны не все, статус `PARTIAL`
- Настройки запроса: `n_ctx` 1024, ответ до 48 токенов, `temperature` 0,2, `top_k` 20, `top_p` 0,9, `seed` 42
