# Длинные записи

Часовой подкаст не должен держаться в памяти целиком. Поэтому звук читается блоками, распознавание идёт срезами, диаризация окнами, а ход работы пишется на диск.

## Как работает

- Декодирование потоковое: память не зависит от длины файла, `pcm16k.wav` занимает 115 МБ на час
- Чтение звука блоками, в память попадает только текущий срез или окно
- Распознавание идёт срезами до 22 секунд, после стадии модель выгружается
- Диаризация идёт окнами по 5 минут: нативный метод держит весь сигнал в куче и строит квадратичную матрицу, поэтому целиком файл не подаётся
- Перед следующей стадией модель прошлой закрыта: две тяжёлые модели вместе не лежат в памяти
- Чекпойнты после каждого среза и окна: обрыв на 40-й минуте не отбрасывает работу, см. [14. Продолжение после прерывания](14-recovery.md)
- Если запись дольше 15 минут, окна языковой модели меньше: 300 токенов вместо 450, а бюджет не выше 90 секунд
- Список реплик виртуальный, лента говорящих считается заранее, поэтому экран результата не зависит от числа реплик

## Как проверить

Перед началом: Главная, запись от 15 минут `long.mp3`, лучше час.

1. Импортируйте запись и смотрите счётчики - счётчик окон на этапе «Определение говорящих» растёт, стадии идут по порядку
2. Во время обработки выполните `adb shell dumpsys meminfo ru.stenokot.app` несколько раз - значение `TOTAL` не растёт от окна к окну
3. Дождитесь конца - `metadata.json` содержит `vm_hwm_kb`, времена стадий, `rtf_core` и `rtf_full`
4. Откройте результат и прокрутите список - прокрутка плавная
5. Откройте протокол - если обработана часть окон, статус частичный и видны покрытые интервалы

## Ограничения

- Память на записи 60 минут не измерена. На записи 3 минуты пик 803 МБ на диаризации: эмулятор arm64, 4 ГБ RAM, 4 vCPU, API 36, хост Mac M4, отдельные стадии, не готовый APK
- Время обработки часовой записи не измерено
- Android 15 ограничивает службы обработки 6 часами в сутки
- Покрытие протоколом длинных записей ограничено бюджетом
