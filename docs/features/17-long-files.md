# Длинные записи

Часовой подкаст не должен держаться в памяти целиком. Поэтому звук читается блоками, распознавание идёт фрагментами, диаризация окнами, а ход работы пишется на диск.

## Как работает

- Декодирование потоковое: память не зависит от длины файла, `pcm16k.wav` занимает 115 МБ на час
- Файл больше 256 МБ с постоянным доступом читается на месте, без копии
- В память попадает только текущий фрагмент или окно
- Распознавание идёт фрагментами до 22 секунд
- Диаризация идёт окнами по 5 минут: нативный метод держит весь сигнал в куче и строит квадратичную матрицу, поэтому целиком файл не подаётся
- Уточнение говорящих читает звук по одной фразе. На записи длиннее 1500 фраз группируются 1500 равномерно выбранных, остальные назначаются проходом
- Перед следующей стадией модель прошлой закрыта: две тяжёлые модели вместе не лежат в памяти
- Чекпойнты после каждого фрагмента и окна: обрыв на 40-й минуте не отбрасывает работу, см. [14. Продолжение после прерывания](14-recovery.md)
- Языковая модель берёт не больше 60 окон, выбранных равномерно по записи
- На Android 15 службе обработки дано 6 часов в сутки в фоне. По сигналу системы служба переходит на тип без этого лимита
- Список реплик ленивый, огибающая и ленты говорящих считаются заранее, поэтому экран результата не зависит от числа реплик

## Результаты

Запись 57 мин 17 с, один прогон на каждой среде:

| | Honor, Snapdragon 662, полный APK `74bea98` | Эмулятор, `c5cf2e6` |
|---|---:|---:|
| Время до JSON | 3695 с | 291 с |
| `RTF_core` | 1,075 | около 0,085 |
| Распознавание | 1010 с | 110 с |
| Диаризация с уточнением | 2542 с | 158 с |
| Пик памяти | 0,9 ГБ | 1150 МБ |
| Говорящих, реплик, слов | 11, 520, 7246 | 11, 520, 7246 |

На эмуляторе пик вырос всего на 8 % против записи 336 с, то есть память ограничена окном. На Honor диаризация шла в 3 раза дольше на минуту записи, чем на записи 6:22, вероятно из-за троттлинга при долгой нагрузке. Протокол на Honor: `PARTIAL`, 33 окна из 60 за 882 с.

## Как проверить

Перед началом: Главная, запись от 15 минут `long.mp3`, лучше час.

1. Импортируйте запись и смотрите счётчики - счётчик окон на «Определение говорящих» растёт, стадии идут по порядку
2. Во время обработки выполните `adb shell dumpsys meminfo ru.stenokot.app` несколько раз - значение `TOTAL` не растёт от окна к окну
3. Дождитесь конца - `metadata.json` содержит `vm_hwm_kb`, времена стадий, `rtf_core` и `rtf_full`
4. Откройте результат и прокрутите список - прокрутка плавная
5. Откройте протокол - если обработана часть окон, статус частичный и видны обработанные интервалы

## Ограничения

- На слабом телефоне длинная запись идёт медленнее реального времени, основное время уходит на диаризацию
- Записи на 8 часов и файлы на 5 ГБ не прогонялись. Пути для них есть в коде, самый длинный прогон - 57 минут
- Выборка 1500 фраз проверена только модульным тестом: запись 57 минут до неё не дошла
- Протокол на длинной записи покрывает часть окон
